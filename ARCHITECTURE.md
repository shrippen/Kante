# Architecture

How this repository is meant to be built. Where the code differs today is listed under
"Known deviations". Change this file in the PR that changes the structure.

## What it does

Kante is the design system of all shrippen projects: one palette, and from it a
stylesheet for web pages, a QML module for apps, a theme and a UI kit for Kimai plug-ins,
and a style for KDE. The projects build nothing of their own; they link the built
stylesheet or copy the module.

## Building blocks

| Path | Its one task |
|---|---|
| `tokens/palette.json` | The one source of every colour, font, line and level, for all themes (dark, Leinen, Gold). |
| `tokens/variables.css` | The palette as CSS custom properties, and the roles built on them (text, ground, accent, state). |
| `css/`, `js/`, `fonts/` | Kante for the web: the components' styles, their behaviour, the map and wall display scripts, the offline fonts. |
| `qml/Kante/` | Kante for apps: `KanteStyle` (all roles, the one place that picks the theme), one file per component, the skins for Qt's own controls. `KantePalette.qml` is generated. |
| `qml/KantePlasma/` | The few components for Plasma widgets, which keep Plasma's theme. |
| `qml/tests/`, `qml/demo/Gallery.qml` | A test and a gallery entry for every component. |
| `kimai/knust/` | Knust: the Kimai plug-in that gives Kimai Kante's look. Released on its own (`knust-v*`). |
| `kimai/kit/` | The UI kit (`kpu-*`) that every shrippen Kimai plug-in copies in. |
| `union/` | Kante as a style for KDE's Union engine and as KDE colour schemes (a spike). Only `template/` is written by hand. |
| `templates/` | The starting point for a landing page. |
| `tools/build-*.py`, `build.sh` | The build: generates everything below from the sources above. |
| `tools/check-*`, `tools/qmllint.sh` | The checks the build and CI run: tokens, release lists, QML tests, kit, Union. |
| `docs/v1/` | The built web files. `shrippen.github.io` copies them and serves them to every page. Generated. |
| `docs/` (rest), `proposals/`, `README.md` | Kante's and Knust's own pages; design proposals by date, kept as record; the catalogue of every token and component. |
| `.design-sync/` | The bundle for Claude Design, built from the same sources. |
| `tools/release-notes.sh`, `tools/sync-release-notes.sh` | The release-notes tool of all projects and its distribution. |

## Layers

```
                         tokens/palette.json   (the one source)
                                   │ generated by build.sh
      ┌──────────────┬─────────────┼───────────────┬──────────────────┐
      ▼              ▼             ▼               ▼                  ▼
 variables.css   KantePalette   knust-palette   union/ styles     (checks)
      │              │             │             and colours
      ▼              ▼             ▼
 css/ + js/      KanteStyle     knust.css ──► kit.css
      │              │
      ▼              ▼
 docs/v1/        components, skins ──► KantePlasma
      │              │                              │
      ▼              ▼                              ▼
 web pages       apps (copy qml/Kante)      Kimai plug-ins (Knust installed,
 (link /v1/)                                 kit copied in)
```

- A value stands once, in `tokens/palette.json`. Everything else that holds a colour is
  generated from it and never edited by hand.
- No raw colour or font outside `tokens/`. CSS uses the custom properties; a QML
  component asks `KanteStyle`, never `KantePalette`, and never decides the theme itself.
- Generated files (`docs/v1/`, `KantePalette.qml`, `tokens/palette.qml`,
  `knust-palette.css`, `union/styles/`, `union/colors/`) are committed and changed only
  by `./build.sh`.
- A shape or behaviour several components share is written once and used by them: in
  CSS as one rule or property, in QML as one component or function.
- Web and apps show the same thing under the same name; a theme has one name everywhere.
- Knust takes its colours from the generated palette only. The kit uses Knust's and
  Kimai's properties with a fallback, so it also works without Knust.
- Kante knows no project. What only one project needs stays there; what a second one
  needs comes here first and is then used by both.
- Every QML component has a test and a gallery entry, filed under the component's name.
- `tools/` holds what builds and checks Kante, nothing for other repositories.

## Where new things go

| Change | Touch |
|---|---|
| A new or changed colour, font or level | `tokens/palette.json` (and, until they are generated, the same value in `tokens/variables.css`), `./build.sh`, README |
| A new role (what a colour is for) | `tokens/variables.css` and `qml/Kante/KanteStyle.qml`, under the same name; README |
| A new web component | `css/components.css`, behaviour in `js/`, README, `tools/specimen.html` |
| A new QML component | A file in `qml/Kante/`, a test in `qml/tests/`, an entry in `qml/demo/Gallery.qml`, README; `./build.sh` writes `qmldir` |
| Motion | The `prefers-reduced-motion` block at the end of `css/components.css`; `KanteStyle.motion` in QML |
| Something for Kimai's look | `kimai/knust/`; something Kimai plug-ins share: `kimai/kit/`, then `kimai/kit/bin/sync.sh` per plug-in |
| A theme or variant | `tokens/palette.json`, its block in `tokens/variables.css`, `KanteStyle`, the build scripts that list themes |
| A proposal before it is built | `proposals/<year>-<month>-<name>/` |
| After any change | `./build.sh`, commit the generated files; then `./build.sh` in `shrippen.github.io` |

## Known deviations

- Every colour stands by hand in `tokens/variables.css` as well; a check compares the
  two. Kante Light's colours stand only there (`AUDIT.md`, finding 3).
- The Union build calls Leinen "Kante Light", which is another theme
  (`AUDIT.md`, finding 4).
- The staffs for bass and tablature build the same frame twice, and four components
  each keep the note state themselves (`AUDIT.md`, finding 1).
- Three charts each compute their own axis steps (`AUDIT.md`, finding 2).
- The cut corner is written out about 25 times in the stylesheet
  (`AUDIT.md`, finding 7).
- `js/shrippen.js` does everything in one function (`AUDIT.md`, finding 5).
- Tests and gallery are filed by version number, not by component
  (`AUDIT.md`, finding 6).
- Two components read `KantePalette` directly (`KanteSticker`, `KanteRehearsalMark`;
  not in `AUDIT.md`).
- The release-notes tool of all projects lives here (`AUDIT.md`, finding 8).
